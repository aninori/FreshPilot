Proof of concept · Fresh grocery operations

FreshPilot

An agentic layer for fresh-food ordering. Machine learning forecasts the range of demand, deterministic math decides the order, and LLM agents investigate exceptions, explain every number, and escalate only what a manager needs to see.

Messy data→ Clean catalog→ ML forecast→ Order decision→ Agent review→ Manager

The problem

Fresh departments break the assumptions most retail systems are built on. Three blind spots drive waste and empty shelves at the same time.

01

Messy item data

The same banana appears as three SKUs with different names and units across vendor feeds, so demand history gets split and orders get miscalculated.

02

Phantom inventory

Spoilage, shrink, and miscounts go unrecorded. The system shows stock that isn't on the shelf, so it never reorders.

03

Point forecasts

A single demand number hides risk. For perishables, the cost of over-ordering and under-ordering differs by item and must be weighed explicitly.

How it works

Five stages. Deterministic code and ML compute every number; LLM agents only review, investigate, and explain.

Input

Messy source data

Vendor catalogs, POS sales, receipts, shrink logs, promotions, weather.

↓
Stage 1 · Deterministic

Catalog reconciliation

Parse units ("CS/12 5LB" → 60 lb), embed and fuzzy-match names, score each match. High confidence merges automatically.

Stage 1 · Agent

Match review agent

Reviews only the uncertain middle band and proposes merge or keep-separate with evidence. A validator applies the decision.

↓
Stage 2 · ML + math

Forecast and order engine

LightGBM quantile model predicts P10–P90 demand, conformal calibration keeps intervals honest, and a newsvendor optimizer turns the range into a case-rounded order.

No LLM here. Order quantities are always computed, never generated.
↓
Stage 3 · Deterministic

Exception detector

Flags phantom stock (Poisson test on unexpected zero sales), shrink spikes, large order swings, and low-confidence catalog matches.

Stage 4 · Agent

Investigator agent

Uses tools to pull history and forecast drivers, recommends an action, then auto-approves routine items or escalates risky ones.

↓
Stage 5 · Output

Manager dashboard

A short escalation queue with plain-language explanations, plus waste and stockout metrics against a baseline ordering policy.

Deterministic / ML: computes and decides LLM agent: reviews and explains

Agent workflow

The investigator runs as a LangGraph state machine. The LLM sits in the middle, fenced by deterministic steps on both sides.

triage→ investigate→ validate→ route→ narrate

Agent tools

get_sales_history, get_inventory, explain_forecast (SHAP drivers), simulate_order, get_catalog_match. The agent can only read data or run the engine; it cannot write an order directly.

Structured output

Every finding returns a Pydantic object: finding, evidence, recommended_action, risk_level, route. Numbers in the narrative are checked against source data before display.

Guardrails

Any quantity change must come from simulate_order and stay within a policy band. Actions above the risk threshold pause for manager approval.

Routing

Routine, low-risk items are auto-approved with an audit note. Only high-risk or low-confidence items reach the manager queue.
